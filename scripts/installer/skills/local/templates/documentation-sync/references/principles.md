# Principles

What earns a place on a page, and what has to be cut. Load this before writing, keeping, or
judging any sentence.

## What a doc page is for

A page makes the *shape and why* of the system reachable without re-deriving it from the
source. It says which part of the repo owns a responsibility and why it exists in that form,
so a reader can open the right file. It stops where the code begins.

Pages therefore carry what changes slowly — responsibilities, decisions, motivations — and
never what changes fast.

## Two questions that decide what belongs

Nearly every bad addition satisfies all six rules and fails one of these.

**1. Does the reader *set* this value, or does the repo *contain* it?**

- **Input contract** — a value the reader sets to change behavior: an env var, a flag, a CLI
  command, an extension-point file a contributor edits. Name it. A rename here is a real
  change that *should* reach the docs.
- **Shipped default** — a value the repo carries inside a file: template contents, default
  preferences, a marker's exact bytes. Never name it, and do not enumerate the categories
  either. Say the file exists and what it is for; the reader opens it for the values.

**2. Whose behavior is it?**

- **This repo's** — a decision made here. Documentable, together with its why. Mechanism is
  allowed when the decision *is* the mechanism.
- **A third party's** — a tool's internal algorithm, fallback order, or defaults. Never. Point
  at the upstream tool instead. This is the only class of claim that can turn false with
  nobody touching this repo, and it is unverifiable against the code, so no rule and no
  automated check will catch it.

## The admission test

Before adding a sentence — or keeping one you are editing around — ask, in order:

1. **Does it say more than the identifier it names?** "`retry.sh` — retries flaky operations
   with backoff" is the filename plus adjectives. Cut it.
2. **Is it checkable?** A factual claim must be verifiable against this repository's code. A
   *why* cannot be, and is held to attribution instead: it must name the constraint it answers
   or the alternative it rejected. A why that names neither is an opinion.
3. **Does it survive a rename, a changed default, or an upstream release?** If not, raise the
   altitude or point at the source.
4. **Does the reader need it to know where to look, or is it a value they would read from the
   file itself?** Point, don't mirror.

Any "no" means cut the sentence or raise its altitude. Softening the wording is not a fix.

## Claims that are not about now

"For now", "currently", "will soon": neither verifiable nor attributable, and to a reader who
takes the page as authoritative they are indistinguishable from facts. Keep them out of pages.

The exception is a deprecation the code carries — a flag, a shim, a warning it emits. That is
not a prediction but a current input contract, and it is documented as one. Roadmap and
intent go in the top-level document the index links, never inside a page.

## Code examples

The same discriminator, applied to a block instead of a sentence. An example earns its place
when the example *is* the input contract: an invocation, a public signature, a key the reader
sets. It does not when it illustrates how something works inside — that is mirroring in block
form, and it is the shape that goes stale fastest.

## Worked examples

Each ✗ below is the kind of edit that has to be reverted.

**A shipped default, and third-party mechanics.**

- ✗ The template carries a colour theme and `terminal.new_cwd = "current"`, so new panes start
  in the launch directory instead of falling back to the home directory.
- ✓ The template carries a small set of default preferences.

Two failures in one sentence: it names a value the repo ships, and the clause after "so"
explains an upstream tool's fallback logic. Note that even naming the *categories* ("a colour
theme and a working-directory default") is too much — the reader opens the file.

**A directory inventory.**

- ✗ A table with one row per file in a source directory: `logging.sh` — consistent, leveled log
  output; `retry.sh` — retries flaky operations with backoff.
- ✓ Name the directory, say what the layer is responsible for and why it exists, and point at
  the files for the rest.

The form is the defect: an inventory is silently incomplete the moment a file is added, and a
row that restates its own filename never earned its place.

**An internal symbol.**

- ✗ …generated by `renderTemplateTree()`.
- ✓ Describe what the generation step produces.

**Exact bytes.**

- ✗ The `.format-version` marker contains exactly `1` plus a newline.
- ✓ Say that the file records the format version.

**Legitimate mechanism, for contrast** — this belongs on a page:

- ✓ The public command is a thin wrapper: it sets `XDG_CONFIG_HOME` and execs the real binary,
  so config and sockets stay per-project.

It names an input contract, describes a decision made in this repo, and gives the why. "Never
explain mechanism" is the wrong lesson to take from the examples above.
